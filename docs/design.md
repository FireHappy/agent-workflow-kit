# 设计说明

## 一句话

把「项目事实」与「生成物」分开：事实写在项目里，入口和状态由工具生成，生成结果可校验。

## 三层结构

| 层 | 位置 | 内容 | 谁维护 |
|---|---|---|---|
| 框架 | `agent-workflow/` | 规范正文、工作流、账本、工具 | 技能生成后随项目演进 |
| 事实 | `agent-workflow/project.yaml` | 名字、别名、校验命令、并行切分、共享写点 | 人 |
| 入口 | `<repo>/AGENTS.md` | 开工顺序、铁律、验证命令、并行提示 | `awf bootstrap` 生成 |

全局还有一层：`~/.agents/projects.tsv`（数据）与 `~/.agents/AGENTS.md`（视图），用于跨项目定位。

## 为什么入口是产物

1. 各 harness 只读仓库里的文件；入口必须落在仓库根，不能放在技能目录里。
2. 入口里的规则是通用的，事实是每个项目不同的；用模板 + 变量把两者分开，避免手写漂移。
3. 入口带 `digest`：事实或模板变了但没重建，`awf check` 直接失败。

```text
<!-- awf:begin v1 digest:xxxxxxxx -->
...（受控区块）
<!-- awf:end -->
```

`bootstrap` 只替换区块内部，区块外由人自由编辑，因此“团队约定”不会被覆盖。

## 为什么 status 是产物

`tasks/status.md` 是 `tasks/*/current.md`、`todo.md`、`done.md` 的投影。手抄三份必然漂移，所以：

- `awf status` 生成 `<!-- awf:status:begin -->` 区块；
- 区块外保留“已验证功能 / 临时记录”等人工内容；
- 归档前必须跑 `check`，失败即不算完成。

## 校验策略

`awf check` 检查四类：

1. 框架文件齐全（入口、事实、五份流程、模板、状态）。
2. `AGENTS.md` 的 digest 与 `project.yaml` + 模板一致。
3. 每个进行中任务块包含 `状态` / `Owner` / `下一步`。
4. 迁移类 FAIL（归档块缺「状态」、旧英文表头 `| Status |`）输出**可直接执行的修复指引**，agent 无需推断。
5. 退出码 = 失败项数量，可直接给 pre-commit / CI 用。

确定性检查优先于“请记得更新”这类文字约束。

## 全局索引

- 数据：`~/.agents/projects.tsv`，一行一个项目（`id | 别名 | 路径 | 入口`）。
- 视图：`~/.agents/AGENTS.md`，由 `awf register` 渲染，DSH 作为用户级上下文注入。
- 自愈：`awf init` 自动登记；`bootstrap` 只刷新已登记项目的路径，避免意外写入。

索引只放指针，不放项目细节；它是上下文里最泛化的一层，必须保持小。

## 并行约定

`project.yaml` 的 `scopes` 描述可并行单元，`serialized` 描述任何并行单元都不得同时修改的文件（如 `manifest.json`、`tasks/**`）。

配套原则：账本单写者。子任务只返回结果，由主线合并 `current.md`，避免多写者冲突。

## 跨项目派发

跨项目不是把 cwd 切过去，而是先过四道门：目标工作流、目标工作区、可写、会话通道。全过时用 `awf-dispatch` 在目标工作区创建正式会话，任务留在会话里可继续追问；headless 仅作为无人值守回退。

核心与适配分离：`workflows/cross-project.md` 是 harness 无关规范，`bin/awf-dispatch` 是 DSH 适配器；其他 harness 可用 GUI 手工会话，语义相同。

## 激活式 Router（任务派发边界）

跨项目派发在「谁有资格路由」上进一步收紧：**激活式 router**——路由能力不是常驻身份，只在节点直面**用户原始请求**时临时激活。

### 为什么

worker/router 对偶模型下，任务无限转包会稀释责任、膨胀票据、搅乱账本。前例：

- DEV-042 自动回填空转已停用（机器空转不产生价值）；
- 2026-11-01 七人改六仓库：任务归属凌乱、changedPaths 门禁卡死，需 amend 契约绕过。

### 三条规则

1. **激活条件唯一**：只有直接面对用户原始请求的节点才临时激活为 router；来源为「工作流任务」（另一节点派发）的节点一律保持 worker，只执行。
2. **派发深度 = 1**：被派发方不得再转派。任务票据头部携带「来源：用户 | 工作流」标记；来源=工作流的票据若再次用于派发，视为违规（`awf-dispatch` 直接 FAIL，退出码 2）。
3. **router 决策三件套**：分析用户意图 → 检索全局索引（`awf projects` / `awf find`，即"工作群"）→ 综合决策（自己干 or 派给谁/通道）；决策结论**落盘到票据头部**（来源 + 路由裁决：目标 / 通道 / 理由），不留在模型头脑里。

拓扑：用户为根，派发边深度 = 1 截断，全局无环（DAG），杜绝 A→B→A 循环转包。

### 示意一：激活派发（用户 → router(激活) → worker 执行 → 回报）

```text
用户原始请求
   │  票据头部：来源=用户
   ▼
节点 A（router 临时激活）——决策三件套：分析意图 → awf find 检索全局索引 → 综合决策
   │  路由裁决落盘：目标=<项目B> / 通道=awf-dispatch / 理由=...
   │  票据头部：来源=用户（+ 路由裁决）
   ▼
节点 B（worker，派发深度=1：只执行，不转派）
   │  完成：账本归档 → check → awf status → 本地 commit
   ▼
回报（任务包五项）→ 节点 A 汇总 → 用户
```

### 示意二：worker 转派被拒

```text
节点 B（worker：收到的票据来源=工作流，只有执行权、没有路由权）
   │  试图再派发：目标=<项目C>，手持票据来源=工作流
   ▼
awf-dispatch 来源校验（ticket_source）
   │  来源=工作流 → 违规
   ▼
FAIL「禁止转派：……派发深度 = 1，接收者保持 worker 只执行……
      如需转包，请由用户创建「来源：用户」的新任务票据」（退出码 2）
```

机制上没有「转包链」：任何被派发节点出手再派发，都会在派发器这一关被截断。

### 示意三：按 role（特长）派发（DEV-122）

```text
用户原始请求：生成日报并总结本周 git 提交
   │  票据头部：来源=用户
   ▼
节点 A（router 临时激活）——决策三件套：分析意图
   │    → awf find / awf projects 检索工作群：逐 worker 带出 role（特长）
   │      周报  → 擅长收集 DSH 会话历史与 git 提交，归纳生成日报/周报  ← 候选命中
   │        pluto → 擅长 Rokid AR 系统镜像定制（不匹配，排除）
   │    → 综合决策：目标=周报；通道=awf-dispatch；理由=role 匹配
   │      （擅长收集会话+生成报告，对应日报任务）
   │   awf-dispatch 周报 <ticket> --check-role   （软校验：关键词交集命中，无警告）
   ▼
节点 周报（worker）执行 → 回报五项 → 节点 A 落盘票据头部裁决 → 用户
```

要点：role 是**匹配依据**不是装饰字段；`--check-role` 只做关键词**软校验**（不匹配警告 / 无 role 提示，均不硬拒，避免误伤合法派发）；路由裁决理由必须写明「目标 role 与任务意图的匹配说明」（见 `agent-workflow/workflows/cross-project.md` 第 4 条），匹配不到时写「无匹配，建议用户确认」不得硬凑。匹配算法（DEV-123）：中英文关键词交集——英文词（≥3 字母，小写归一）+ 中文 2/3/4-gram，并剔除泛词停用表（生成/校验/开发/管理/目标/任务等，不构成领域特征）；泛词不再单独构成匹配依据，领域 2 字词（周报/联调/镜像）单命中即算匹配。

## worker 名牌（role）

worker/router 对偶模型下，每个已登记项目是网络中的一个 worker；寻址（id / aliases / 路径）已通，但 router 检索工作群时看不到「这个 worker 是干嘛的」。DEV-118 引入可选的 **role** 字段作为 worker 名牌（一句话自述）：

- **怎么填**：在项目 `agent-workflow/project.yaml` 加一行 `role: <一句话：这个 worker 主要承担什么>`；由各项目自己注册（`awf register` 即完成名牌登记，无需改索引）。**init 即登记（DEV-121）**：`awf init --role "能力自述"` 初始化时就把能力写入 `role:` 键（模板 `{{ROLE}}` 占位）；缺省保留空 `role:` 键并在完成提示中给出填写指引。模板不预置**字面**空 `role:` 键（避免空键行被解析器当成「有值前的占位」吞掉后填值，DEV-119）；`yaml_get` 只取**非空值**的匹配行，空键/双 role 键自动跳过、取第一个有值项，向前兼容（初始化后的角色可随时补充，立即生效，无需 re-register）。
- **单一事实源**：role 只存在 yaml，不改 `~/.agents/projects.tsv` 列结构——索引只放指针，避免索引漂移（role 改了不用 re-register，寻址时实时读 yaml）。
- **怎么带出**：`awf find <别名|ID>` 输出 `id\t路径\t角色`；`awf projects` 表格含「角色」列；两者 role 缺省回退到 `name`，再缺省输出 `-`，向后兼容。
- **register 提示**：登记时无 role 输出填写提示，有 role 输出「已登记 worker 名牌」。
- **router 怎么用**：检索工作群（`awf find` / `awf projects`）时角色说明随行带出，路由决策更精准；**权限（ACL / scopes 校验 / actions 白名单）本轮明确不做**，role 只是可读名牌，无校验语义。
- **派发票据**：票据头「目标项目：<别名>（<绝对路径>）」仍是唯一目标来源；「目标 worker：<别名>」别名寻址与路径语义会引入第二条寻址线，影响面大，本轮只做文档说明不强改解析——需要角色信息时在寻址侧（find/projects）带出即可。

## 经验/工具积累闭环（worker 记忆）

每个 worker 有 `agent-workflow/memory/{cache,history}/`（短期证据 / 长期结论）与 `agent-workflow/tools/`（可复用脚本手册）。DEV-124 把它串成闭环（**流程引导，非硬门禁**）：

```text
开工：先读 history 同类经验（修复类读修法、生成类读教训）
  │
  ▼
执行任务（current.md → done.md）
  │
  ▼
收尾：可复用结论（根因/修法/决策/坑）→ history/<主题>_<日期>.md
      可复用脚本 → tools/（晋升三要素：可执行 + 用法注释 + 归属）
  ▼
check 软提示（只提示不 FAIL）：归档 ≥3 但 history 空 → 建议沉淀
```

- **沉淀时机**：任务归档时、问题解决后、发现反直觉行为时；**可复用 = 根因与修法 / 技术决策 / 踩坑与规避 / 可复用命令**四类，一次性琐事不存（存 cache 或删除），标准见 `memory/README.md`。
- **tools 晋升三要素**：① 可执行文件（shebang/入口）② 用法注释（用途/参数/示例）③ 归属明确（该 worker 的重复性操作）；`awf upgrade` 保留 memory/tools 不覆盖（DEV-116 既定）。
- **软校验**：`awf check` 在归档 ≥3 且 history 无沉淀 / tools 无脚本时输出「提示」（say，不计入 FAIL）；有沉淀后提示消失。**明确不做**：强制门禁、跨 worker 经验共享（写全局索引属后续 r/w 边界议题）、自动升级脚本为工具。

## 版本

`VERSION` 是技能版本；入口区块记录 `v<version>`。升级项目是一等操作：`awf upgrade <目录>` 复制框架文件 → `bootstrap` 刷新入口 → `check` 校验，保留 `project.yaml` / `tasks/**` / `memory/**` / `tools/**`；步骤与验收见 `docs/upgrade.md`。

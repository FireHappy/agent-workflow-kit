# 派发会话「物理删除」能力排查：宿主无可用删除路径 → 归档退役 + --session 锁定

关联任务：SESSION-20261108（DELETE-SESSION-20261108-1，2026-11-08）。
目标：验证 DSH 是否提供会话物理删除 / 销毁能力，并给 awf-dispatch 配套。

## 背景

用户要求放弃复杂复用池，改为「每次 `--new` 新建 → 任务完成核验后**物理删除该会话**」。
派发方初查只看到 `workspace/archiveSession`；随后在 asar 里发现 `session/delete` 字样并质疑结论，
本文件记录补证后的定稿结论（含 ACP 协议层 vs DSH 实现的区分）。

## 结论：DSH 0.2.2-rc.1 **没有可用的会话物理删除能力**

### asar 中 `session/delete` 的真实归属（补证）

逐文件扫描 asar（20529 个文件）后，`session/delete` / `deleteSession` / `zDeleteSessionRequest` /
`AGENT_METHODS.session_delete` 只出现在：

| 位置 | 性质 |
|---|---|
| `@agentclientprotocol/sdk`（`dist/acp.js`、`schema/`、`schema/zod.gen.js`、测试） | 第三方 **ACP（Agent Client Protocol）SDK**：协议 schema、client 方法 `deleteSession()`、agent 侧可选注册、协议测试 |
| `dsh-session-query-sqlite/lib/index.js` | SQLite FTS **搜索索引**的 `_deleteSession` |
| `dsh-experimental-inspector/.../application-*.js` | Chrome DevTools 的 device-bound session（无关） |

### A. 语义与调用路径

- `session/delete` 是 ACP **agent 侧**请求：ACP client（脚本 / 测试驱动）→ agent，参数 `{sessionId}`
  （`zDeleteSessionRequest`），返回空对象；仅在 agent `initialize` 声明 `sessionCapabilities.delete`
  时可用。JSON-RPC（stdio/WS），**不是 MCP**，也不是 DSH dashboard 的 `/api/*` RPC。
- DSH 侧 Web RPC 端点清单（`dsh-api-session-controller` / `dsh-api-workspace-controller` 的
  `typert.host.js`）**没有任何 delete/destroy/purge**；实测 `POST /api/session/delete`、
  `/api/session/destroy`、`/api/workspace/deleteSession` 均 **HTTP 404「DSH Web 不支持端点」**。

### B. 宿主是否实现 `implementation.deleteSession`

**否**。`@deepseek-ai/dsh-acp`（DSH 的 ACP server）：

- `initialize` 只声明 `sessionCapabilities: {close, list, resume}` —— **没有 `delete`**；
- 连接只注册 `session.new/list/resume/close/setConfigOption/prompt/cancel`，
  **没有 `deleteSession` handler**；
- README 明写：「Persistence supports listing, resuming, and closing sessions across process restarts,
  **but deletion, forks, transcript replay, and additional directories are unsupported**」。

### C. 排除理由（不止查 destroy/purge）

1. `session/delete` 全部来自 ACP SDK；DSH 包没有调用 SDK client 的 `deleteSession()`。
2. DSH 作为 ACP agent 不实现 / 不声明 delete；dashboard 也没有对应端点（404 实测）。
3. `_deleteSession`（sqlite）= 删 FTS 索引行（`persisted_docs` / `temp.live_docs`），不是会话数据、不暴露。
4. inspector 的 `deleteSession` = DevTools device-bound session，无关。
5. `it.each([... "session/delete" ...])` 是 SDK 协议测试（无 session header 时拒绝），不是 DSH 行为。
6. `workspace/archiveSession` = 「从工作区分组界面隐藏」；`workspace/delete` = 「Remove one Workspace registration while retaining files and
   Sessions」（保留文件与会话）；会话右键菜单只有 pin/rename/fork/id/archive；会话后端文档自述
   「**不删除会话文件**——日志在 root 下累积，直到外部移除；seam 无删除接口」。

**综合：Dsh 侧无任何可从 dashboard / ACP / 公开 API 到达的物理删除路径。**

## 决策：归档退役，不伪造 / 硬删文件

`awf-dispatch --retire-session <会话ID> [--apply]`（仅 `[awf]` 派发会话，非派发用户会话拒绝）：

- 默认 dry-run；`--apply` 调 `workspace/archiveSession`，并写本地归档台账
  `.dispatch/archived-sessions.json`（该 id 从此不进复用池、不参与每项目数量统计）。
- 与物理删除的差异（必须如实转述用户）：**不回收磁盘**、**可由 `workspace/unarchiveSession` 恢复**、
  `~/.dsh/sessions/<cwd>/<session-id>/` 仍在。脚本不 `rm` 任何会话文件。
- 推荐流程：`--new` 派发 → 必报点 10 完成回执 → 派发方核验 → `--retire-session <ID> --apply` → `--prune` 票据。
- 将来宿主提供删除 RPC（如 DSH 实现 ACP `session/delete` 或 dashboard 端点）时，替换 retire 的 archive 调用即可。

## 附带修复：`--session` 硬指定不得改选（派发方实测 bug）

现象：`--session <id>` 指定会话 busy 且项目 `[awf]` 池 ≥3 时，`wait_session_ready` 会启动整池监听
子进程，并采用监听返回的其它空闲会话，导致追问误投（实测投到承载其他任务的 `session-23c9a97c`）。

修法：`wait_session_ready(..., allow_reselect=False)` —— `--session` 路径只 `wait_for_idle`
指定会话，**不启动池监听、绝不改选**；`dispatch_session` 调用处再加一道「返回会话 ≠ 指定会话即中止」
防御。复用/自动选池路径保持 DEV-224 的整池监听语义不变。

## 附带结论：新建会话的「权限牌」一致性

- DSH 在**创建会话时**读取 profile 的 `permission.defaultPreset`（设置命名空间 `permission`），
  并写入会话的 `permission/preset`；`session/create` 请求没有权限参数。
- 因此 **GUI 新建与 `awf-dispatch --new` 新建默认继承同一权限预设**；当前机器实测
  `permissionPresets/catalog` → `defaultPreset = danger-full-access`，当前会话
  `projections.values.permissions.currentValue = danger-full-access`。
- 新增只读自检 `awf-dispatch --permission-state`（打印默认预设 / 可选默认 / 当前会话权限）。
  要修改默认值走 GUI「设置 → 权限」或 `settings/mutate ns=permission path=["defaultPreset"]`；
  无法按单次派发单独授权（宿主 create 接口无此参数）。

## 验证

- `python3 -m py_compile awf-dispatch`；`--help` 含新参数；互斥参数组合退出码 2。
- 真实 GUI：`--permission-state` 输出 danger-full-access；`--retire-session` dry-run / 未知 id 报错；
  dry-run 不写台账、不改会话。
- 桩测试（临时 cwd + FakeApi）：retire dry-run 不归档、apply 归档并写台账、重复幂等跳过、运行中拒绝、
  未知 id 拒绝、非 `[awf]` 用户会话拒绝退役。
- `wait_session_ready` 桩测试：`allow_reselect=False` 只等指定会话（未触发池监听）；
  默认路径仍可在满池时改选（DEV-224 行为不回退）。
- 冒烟 / `check_workflow.sh` 见任务归档记录。

## 踩坑（复用）

- 看到 asar 里的方法名先归属到「哪个包」：第三方 ACP SDK 的协议字符串 ≠ DSH 宿主能力；
  `dsh-acp` 的 `initialize` 能力声明 + 连接注册表才是「是否实现」的判据。
- 宿主 Web RPC 是 `POST /api/<endpoint>`（`{"type":"client-request","method":...,"payload":{"args":{...}}}`）；
  无参数端点传 `{}`，不要传 `{"_request": {}}`（gateway 校验会报 unexpected "_request"）。
- 探测未知端点返回 404「DSH Web 不支持端点」，可据此区分「无此端点」与「参数错误」。
- `--session` 是「显式指定」，与复用池语义相反：等待逻辑必须允许关闭改选，不能复用满池监听。
- 归档台账按 **派发方 cwd** 落盘（`.dispatch/archived-sessions.json`），不同派发方各一份；
  退役命令与 `--cleanup` 共用台账与 `record_archived_sessions`，避免两套口径。

# git worktree 用于派发隔离（G3 门禁优化候选）评估结论

日期：2026-11-04 ｜ 关联：DISPATCH-140（dsh-im）→ DEV-149（本仓库）｜ 类型：架构评估（docs 流程，未改代码）

## 背景

门禁 G3（可写检查）在两类场景阻断 `awf-dispatch`：目标主仓库有已跟踪改动（他任务改到一半）→ G3 dirty；目标账本有 active 任务 → G3 active。候选方案：用 `git worktree` 让每个派发在**独立工作树 + 独立分支**上执行、完成后 merge 回收，从而**移除 G3 检查**，把检查点从「派发前入口」挪到「merge 出口」（真实冲突极低，出口由派发器引导解决；merge 后 `awf status` 重生成账本摘要 + check 作为出口校验）。

评估曾有一次修正（以修正后为准）：账本（tasks/<ID>.md）是"记录任务"的、每任务独立文件，多 worktree 各自 checkout 后 **merge 自动合并不同条目，不构成分叉阻断**；可再生产物（status.md / README.md）merge 冲突后重跑 `awf status` 重新生成即可（免疫冲突）。

## 核心结论：缓做（design-ready），当前不实现

**触发条件成熟前不做**。理由：

1. **当前场景无收益**：派发流量以「框架升级类」为主（一个项目一个仓库、顺序执行），同类高频并行开发少——同一仓库内多任务并行是稀缺场景，worktree 隔离的收益 ≈ 0，而成本是实打实的架构改造（见证据②）。
2. **低成本替代已落地**：DISPATCH-139（P1 `--allow-dirty=tasks` 豁免账本自我生成物 + P2 G1 瞬态降级 warn）已消除当前多数 G3 卡点，零架构成本；先吃满它再考虑 worktree。
3. **架构成本集中在会话/工作区/复用三重身份绑定**：worktree 改变了仓库路径身份，而 `select_reuse_session` / `find_workspace` / `DshApi.create_session` 全部按「路径 = 工作区」绑定，改动面横跨派发器生命周期，且伴随未覆盖的会话回收缺口（见证据②、风险④）。

**何时做（触发信号，满足任一即可立项为 DEV）**：
- 同一目标仓库出现**同仓并行开发**需求：连续派发同一 repo 的不同 dev 任务，且 P1/P2 豁免后仍被「业务代码脏 / active 任务」卡住排队（queue-timeout 频繁触发、串行化损失明显）；
- 用户明确要求「真隔离」（防上下文污染 / 防一个仓库被多会话误写），不再接受合并写；
- 派发器已具备会话回收能力（DshApi 有 session close/delete），缺口④收敛。

## 若做：设计要点（design-ready 留档）

1. **分支与目录约定**：主树默认检出 `dev`，`git worktree add` 同分支受限 → 每派发从 `dev` HEAD 建独立分支 `dsp-<目标项目>-<票据ID>` 并检出到**主仓库之外**的目录（如 `~/agent-worktrees/<项目>-<票据>/`）——放仓库内会让主树 `git status` 出现未跟踪目录，破坏隔离语义；命名含票据 ID 便于 merge 后回收与排障。
2. **G3 语义变更**：worktree 模式（`--worktree`）下跳过 `check_git`（主树脏与 worktree 无关）与 `check_active`（分支隔离 + 账本按条目 merge；worktree 检出里仍有他人 active 文件，但**不再当阻断**，改为出口 merge 校验）；保留 G1/G2/G4。`--worktree` 是显式 opt-in，与默认复用/`--new` 并存规则：默认复用不变；`--worktree` 与 `--reuse` 互斥（隔离即不共享会话）、可与 `--wait`/`--session` 之外的常规参数组合。
3. **工作区桥（G2 的关键工程点）**：`find_workspace` 是 `realpath` 全等匹配，worktree 路径不在注册表 → G2 必失败。两条路：a) 每个 worktree `workspace/create`（污染 workspace.json、需回收时一并删注册）；b) 解析 `git -C <worktree> rev-parse --git-common-dir` 定位主仓库 → 复用主仓库工作区 + 依赖 harness 支持「同工作区内会话 cwd 指向任意子路径」（当前 `create_session(workspace_id)` 无 cwd 参数，b 路在派发器侧只写成 interface gap：需 DSH 能力或把任务前缀注入「先 `cd <worktree>` 再动手」，代价是会话内第一步靠约定）。
4. **merge 收尾（出口校验）**：agent 在 dsp 分支 commit 后，派发器在主树执行 `git merge --no-ff dsp-<票据>` → `awf status` 重生成 status/README（可再生、免疫冲突；README/status 有真实冲突时以重生成覆盖，勿手解）→ `check_workflow.sh` 作出口门禁 → `git worktree remove --force` + 删分支。
5. **账本一致性**：agent 在 worktree 里照常认领/归档（写 tasks/current|done/<ID>.md，随 dsp 分支提交）；主树 merge 后天然合并不同条目；同一条目被两任务并发改（罕见）才是真冲突，出口由派发器引导人工解。
6. **落地阻力最小路径**：先做「分支 + worktree + merge 辅助脚本」（不碰 awf-dispatch），跑通一个同仓并行样例验证账本 merge 与 status 重生成的免疫性，再谈进派发器。

## 与 DISPATCH-139（P1/P2）的关系

**补充，不是替代；先后顺序 = P1/P2 先，worktree 后**。
- P1/P2 已在零架构成本下消掉「账本自我生成物脏」「status.md 过期瞬态」两类卡点——这两类恰是 worktree 想解决场景里的大头；
- worktree 只解决 P1/P2 覆盖不到的一层：**同仓库真并行写业务代码**（两任务同时改 src/）。这层当前频率极低；
- 即便上了 worktree，P2 心智（merge 后 status/README 过期属瞬态、重生成而非手解）与出口 check 依然需要；P1 `--allow-dirty=tasks` 在非 worktree 模式照旧有用——两者长期共存。

## 证据（源码事实核对，均于 2026-11-04 实读 bin/awf-dispatch）

- ① 复用按 cwd 身份绑定：`select_reuse_session`（:808）用 `os.path.realpath(row.cwd) == realpath(target)` 过滤同 cwd 会话、再按标题派发者段建复用池、`MAX_SENDER_SESSIONS=3` 并发上限——**worktree 改变 cwd 后复用池语义被击穿**（每 worktree 一个 cwd → 池恒空 → 实际每次新建；若让会话留在主树 cwd 则隔离落空）。
- ② 工作区全等匹配：`find_workspace`（:545）对 `workspace.path` realpath 全等；`load_workspaces`（:531）读 `$DSH_HOME/storages/workspace.json`（默认 `~/.dsh/storages/workspace.json`）——worktree 路径未注册 → G2 失败，需桥接层（见设计要点 3）。
- ③ 会话创建无 cwd 参数：`DshApi.create_session(workspace_id)`（:675）只传 workspaceId；cwd 由工作区路径决定——「会话绑定 worktree」当前只能靠「每个 worktree 注册一个工作区」实现。
- ④ 生命周期缺口：wrapper 只有 `create_session/rename/prompt`，**无 session close/delete**——merge 后若删 worktree，会话 cwd 指向已删路径，复用/查找时 realpath 不匹配只会静默落空（无害但泄漏），回收逻辑无处安放；着陆判定 `wait_for_landing`/`git_head_sha`（:1120/:1177，`git -C <target> rev-parse HEAD`）按 CLI 传入的 target 路径操作，实现期须显式指向 worktree 路径；dsp 分支 commit 在共享 .git 上可见，落地判定本身可用。
- ⑤ 常规 G3：`check_git`（:380，`git status --porcelain --untracked-files=no`）与 `check_active`（:415，扫 `tasks/*/current/*.md`，另兼容旧版 `tasks/<type>/current.md` 大文件块）在 preflight（定义 :1551；调用 :1558-1559）执行——worktree 模式按结论 2 跳过即可，接口上 `--worktree` 与 `--allow-dirty`/`--allow-active` 互斥（语义被隔离替代）。

## 风险与未决问题

- 未决①：harness 是否支持「工作区内的会话 cwd 指向任意子路径」——决定工作区桥走 a 路（每 worktree 注册工作区）还是 b 路（复用主工作区 + 会话内 cd 约定）；b 路的会话内工具会以主树为根，需要任务包注入明确的「本任务工作目录 = <worktree>」指令。
- 风险②：worktree 检出基于 `dev` HEAD 的瞬间快照——派发前一刻主树已有他人未提交改动时，dsp 分支 base 不含它（正常），但 merge 回主树时他人未提交改动与 merge 结果并存，出口 check 会看到脏 → 仍要 `--allow-dirty=tasks` 兜底或提示先提交。
- 风险③：同分支限制是硬约束（`git worktree add` 拒绝已检出的分支）——分支命名必须唯一且回收必须可靠，否则 worktree 目录堆积。
- 风险④（上文）：会话无回收 API，worktree 模式会有僵尸会话残留，需与 harness 侧对齐后再做。

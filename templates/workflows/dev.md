# 功能开发工作流

> 状态入口：`../tasks/dev/`
> 主规范：`../README.md`
> 校验命令：见 `../project.yaml`

---

## 目标

把需求推进到「已实现 + 已验证 + 已 review + 已归档」，需要时触发 debug 或 docs 子流程。

---

## Step 1：认领

1. 从 `../tasks/dev/todo.md` 或用户指令确认任务，分配唯一 `DEV-xxx`
2. 写入 `../tasks/dev/current.md`，至少包含：优先级、状态、Owner、协作模式、来源任务、修改范围、依赖、最近更新、目标、验收标准、下一步
3. 需求不清晰时先澄清，不进入实现

---

## Step 2：方案

- 单 agent、小范围改动：直接实现
- 跨模块或多人并行：先拆子任务，写清修改范围与共享写点
- 根因或依赖不明：先补分析，不要盲改
- 优先复用现有模块，做最小闭环变更，并写明风险与验证方式

详细设计写 `../docs/`，`current.md` 里只留 2-6 行摘要。

---

## Step 3：实现

- 优先改已有文件，避免无必要的新抽象
- 发现新问题先记到 `../memory/cache/`，避免主任务上下文丢失
- 发现阻塞依赖：状态改 `blocked`，写清阻塞点与解除条件
- 并行时严格遵守各自的修改范围

**实现完成 → 立即更新任务状态为 `verify`**（验证阶段）：实现完成不是终点，任务状态必须跟着阶段走，不能停留在 `active`。状态流转：`active`（实现）→ `verify`（验证）→ `review`（复核）→ 归档。

如果本质上是缺陷排查，创建 `debug` 子任务，不要把它写成 dev 的日志堆。

---

## Step 4：验证（强制）

按 `../project.yaml` 的 `compile` / `test` 执行：

```sh
# 示例：命令来自 project.yaml，不要照抄
# <compile>
# <test>
```

要求：

- 写完代码立即验证，不能等到 review 阶段
- 每个开发任务至少有一条可重复的验证方式（测试、编译、最小复现）
- 命令不可用时，在任务块写 `验证阻塞：<原因>`，状态改 `blocked`
- 验证通过 → **立即更新任务状态为 `review`**（进入复核阶段，见 Step 5）

---

## 状态流转纪律（强制，贯穿全程）

任务状态不是装饰，**每个阶段完成必须立即更新任务块的状态字段**，且**进入下一状态前必须双重检查进入条件**。

**状态机**：`active`（实现）→ `verify`（验证）→ `review`（复核）→ 归档；异常分支 `blocked`（阻塞）。

**强制纪律（必须执行）：**

- 实现完成 → 状态改 `verify`（Step 3）
- 验证通过 → 状态改 `review`（Step 4）
- review 返回 `pass` → 状态改「归档」，移入 `done.md`（Step 6）
- 任何一次状态更新后，任务块的「最近更新」同步刷新，并运行 `awf status` 回写摘要

**双重检查（进入下一状态前，两重确认缺一不可）：**

1. **自查**（实现者）：对照该状态的进入条件逐条核对——验收标准是否全部勾选（checkItems = 100%）、验证命令是否通过、依赖是否满足、修改范围是否符合
2. **独立复查**（下游执行者 / 独立子 agent）：进入方重新核对同一组进入条件，不依赖实现者的自述；review 阶段由独立子 agent 执行（见 Step 5），其余转移至少由不同角色/会话复查一次

**未通过双重检查不得进入下一状态**——状态字段先于条件满足就更新视为违规（如验收未 100% 就改 `review`、review 未 pass 就归档）。

---

## Step 5：Review

所有 dev 任务归档前必须进入 `review` 子流程（见 `review.md`）。

**前置条件（进入 review 前必须满足）：验收标准全部勾选完成，checkItems 进度 = 100%。** 验收标准未全部勾选的任务不得进入 review —— review 的对象必须是完整交付，不能带着未验收项送审。

**强制语义：review 必须由独立子 agent 执行并等待其返回。**

- 复核者必须是**独立子 agent**（与实现者不同执行者/会话/角色），实现者不能自审
- 归档**必须等待复核子 agent 返回 `pass`（成功）**；返回前任务停留在 `review` 状态，不得归档
- 返回 `needs_revision` / `reject`（不通过）：任务留在原 dev 任务修复，状态改回 `active` / `blocked`，修复后重新验证再进入 review —— **不通过 → 修复 → 复审 循环直到 pass 为止**
- 不新建任务，除非审查意见已演变成独立需求
- 复核必须**独立重跑** `project.yaml` 的验证命令，不能只读实现者的自述
- 回归范围：除原任务外，至少覆盖被改动模块的相关测试；无法覆盖时写明理由
- 单人环境：无团队能力时，至少换一次会话（或隔时）由独立子 agent 复核，不能同会话自审

---

## Step 6：归档

**前置 gate：review 必须已返回 `pass`（见 Step 5）。review 未通过或未执行，不得归档。**

**归档时序（关键）：review 返回 `pass`（验证完成）的当场，就先把任务状态修改为「归档」，不能等 done.md / status / commit 等文档记录完成后再改状态。** 状态是流程完成的即时指示器——验证通过那一刻该任务已经不是「进行中」，文档记录只是把这一事实落纸。

**第 1 步（当场，验证完成即执行）：状态修改为「归档」**

确认 review 结论为 `pass` 后，立即：

- 将任务状态标记为「归档」：任务从 `current.md` 移到 `done.md`
- 状态摘要中不再列为进行中，归入「最近完成」；归档不是删除，任务是已完成状态

**第 2 步（状态已改归档后，依次执行文档记录）：**

1. 有长期价值的过程写入 `../memory/history/`
2. 清理对应 `../memory/cache/`
3. 运行 `./agent-workflow/check_workflow.sh` 通过
4. 运行 `./agent-workflow/bin/awf status` 刷新摘要
5. 提交一次本地 git commit（**禁止 push**）

## 必问用户

- 需求边界不清楚
- 存在两种以上等价但影响不同的实现方案
- 依赖用户提供环境、账号、设备或业务规则
- 修改影响公开行为但预期不明确

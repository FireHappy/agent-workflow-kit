# 跨项目派发工作流

> 本文件为**跨项目派发权威细则**（四道门 / 三规则 / 必报点 / 回执请求 / 转达回执自包含）；项目级技能文件 `skills/cross-project-dispatch/SKILL.md` 可加载参考（不全局安装）；`docs/dispatch.md` 为条款原文。

> 适用：目标代码/产物在另一个仓库，当前项目只负责调度、拆分与验收。
> 主规范：`../README.md`
> 派发器：`../bin/awf-dispatch`（可选适配器；无此脚本时用图形界面手工会话）。
> 本工作流只写与 harness 无关的流程；派发器的具体命令、退出码与各平台适配细节见派发器文档
> （`docs/dispatch.md`）与派发技能（`cross-project-dispatch`，随 agent-workflow-scaffold 分发）。

---

## 目标

把任务交给目标项目自己的 agent，在**目标项目的工作区会话**中执行；调度方只发任务、收结果，不跨仓库改账本。

---

## 任务路由：先判目标仓库，再选通道

所有任务先按「目标仓库是否 == 当前工作区」决策，**不要在选通道前默认建队**；本工作流是「目标仓库 ≠ 当前工作区」时的通道：

| 通道 | 适用条件 | 反例（不适用） |
|---|---|---|
| 单会话 | 目标仓库 == 当前工作区，且任务小（单行修改 / 只读查询 / 跑一次校验） | 可并行拆分的大任务仍单线程硬做；跨仓库任务 |
| 团队 | 目标仓库 == 当前工作区，且**可并行拆分**（多模块、修改范围不重叠、共享写点已声明、需要独立复核） | **跨仓库任务**：成员会话工作区 = 队长工作区，跨仓库写入会被目标项目门禁/范围校验拦截，或越权改错仓库、任务归属混乱（2026-11-01 教训：7 人团队在调度方工作区直接改 6 个项目仓库，任务归属凌乱、changedPaths 门禁卡死，需 amend 契约才绕过） |
| awf-dispatch | 目标仓库 ≠ 当前工作区（**默认通道**）：目标有工作流（G1）且已登记工作区（G2） | 目标仓库 == 当前工作区却绕一圈派发；前置门不过仍强行派发 |

规则（逐条可执行）：

1. 目标仓库 == 当前工作区：小任务单会话；可并行拆分才用团队。
2. 目标仓库 ≠ 当前工作区：**默认 `awf-dispatch` 派到目标项目自己的工作区会话**；调度方不直接改目标仓库。
3. **派发三规则（DEV-138）**：
   - **默认异步**：派发只发送任务、立即返回会话 ID，主会话不被钉住；需要本回合结果/落地确认时调用方**显式 `--wait`**（`--timeout` 仅对 `--wait` 生效）。
   - **派发即启动子代理**：派发动作就是在目标工作区启动目标 agent 的子代理会话，由它独立完成并回报；**不启用智能体团队承载派发**（无 captain/dispatcher 成员层；多目标=多次派发，默认异步互不阻塞，需要结果时各自 `--wait` 或回到会话查看）。
   - **票据瘦身 + 分析归 worker**：router 只写 用户意图 / 硬约束 / 验收标准 / 路由裁决，不写执行步骤、不做前置侦察；前置分析由目标 worker 在自己的会话里用目标仓库 `tools/` 手册与 `memory/history` 完成，有疑问返回 router / 用户决策。
4. **团队不承载跨仓库任务**：团队只承载本工作区内的并行拆分；跨仓库任务从一开始就走 `awf-dispatch`。
5. 无论哪条通道：账本与 commit 归主线（目标项目自己的账本由目标 agent 写）；只本地 commit，禁止 push。

## 四道前置门（缺一不可）

| 门 | 检查 | 不满足时 |
|---|---|---|
| G1 工作流 | 目标有 `AGENTS.md`、`agent-workflow/project.yaml`、`workflows/`、`check_workflow.sh` | 先 `awf init`（需用户确认），不要向无流程仓库派发；仅「status.md 已过期」瞬态 warn 放行（DISPATCH-139） |
| G2 工作区 | 目标路径已登记为当前 harness 的工作区（工作区清单） | 通过 harness 的工作区管理添加，或 `awf-dispatch --add-workspace`；否则生成交接单（handoff） |
| G3 可写 | 目标 `git status` 无已跟踪改动、无其他 active 任务 | `--allow-dirty=tasks` 只豁免账本自我生成物（status/README/log），业务改动仍拒；active 冲突三选项：等它完 / `--allow-active` / `--new`（DISPATCH-139） |
| G4 通道 | 目标工作区能创建会话（会话服务在线、认证有效、模型可用） | 回退无人值守执行（需用户同意）或手工作业（handoff）；不要用不相关目录参数绕过 |

只读任务可以放宽 G3，但仍建议在会话中执行，留下可追问的记录。

> 门禁严格度（DISPATCH-139）：会话繁忙默认排队最多 `--queue-timeout` 180s，超时前回报中途状态（已等秒数/目标 HEAD/会话产出），不静默超时；`--wait` 回合等待超时同样先回报中途状态。

## 任务包（票据瘦身清单）

派发前写成一份任务文件（如 `dispatch/tasks/<项目>-<ID>-<slug>.md`），**只包含四类信息**：

- **用户意图**：`任务：<ID> <一句话目标>`
- **票据来源与路由裁决（激活式路由）**：
  - `- 来源：用户 | 工作流`（缺省视为「用户」，向后兼容；缺省时派发器按用户来源放行）
    - `来源：用户`：本票据由**用户原始请求**直接触发；接收节点临时激活为 router，可自行决策执行或再派发。
    - `来源：工作流`：本票据由另一节点派发；DEV-128 起接收节点**允许按需继续向下一层转派**（深度不限），转派时更新票据「路由裁决」记录链路。
  - `- 路由裁决：目标=<别名> / 通道=awf-dispatch / 理由=<目标 role 匹配说明>`
- **硬约束**：目标项目与任务 ID；类型 `dev|debug|docs`；可选模块（`- 模块：<名称>`）；修改范围、明确不做什么；提交要求（只允许本地 commit，禁止 push）；**分析归属**（前置分析在本会话内用目标仓库 `tools/` 手册与 `memory/history` 完成，有疑问返回决策）
- **验收标准**：逐条可勾选，含**必须实际执行**的验证命令
- **回报格式（任务包五项）**：状态 / 变更文件 / 验证结果 / commit / 阻塞

**不写执行步骤、不做前置侦察**：router 不替目标 worker 做前置分析（构建指引、历史产物、场景清单等）；目标 agent 用自己的会话与目标仓库的 `tools/` 手册、`memory/history` 完成分析。

任务包不要依赖调度方的上下文；目标 agent 是独立会话。

## 激活式路由（票据来源与派发边界）

跨项目派发遵循「激活式 router」协议。目的：任务无限转包会稀释责任、膨胀票据、搅乱账本（前例：DEV-042 自动回填空转已停用；2026-11-01 七人改六仓库教训）。三条规则：

1. **激活条件唯一**：只有直接面对**用户原始请求**的节点才临时激活为 router，拥有路由/派发权；来源为「工作流任务」（另一节点派发）的节点一律保持 worker，只执行。
2. **允许继续转派（DEV-128）**：任务票据携带「来源：用户 | 工作流」标记（缺省=用户，向后兼容）；「来源：工作流」的票据是已派发任务，接收节点**可以按需继续向下一层派发**。`awf-dispatch` 对来源=工作流的票据只提示核对转派理由与路由裁决，不再 FAIL（见 `docs/dispatch.md` 与 `docs/design.md`）。
3. **router 决策三件套**：分析用户意图 → 检索全局索引（`awf projects` / `awf find`，即"工作群"）并读各 worker 的 role（特长），按任务意图筛选候选（如任务=日报生成 → 候选含 周报；role 是匹配依据，不是装饰字段）→ 综合决策（自己干 or 派给谁/通道）；**决策结论落盘到票据头部**（来源 + 路由裁决：目标 / 通道 / 理由），不留在模型头脑里。
4. **路由裁决理由必备项**：理由必须包含**目标 role 与任务意图的匹配说明**，格式示例：`目标=周报；理由=role 匹配（擅长收集会话+生成报告，对应日报任务）`。匹配不到合适 worker 时理由写「无匹配，建议用户确认」，不得硬凑；判断依据即决策三件套第 2 步读到的各 worker role（`awf projects` / `awf find` 带出；`awf-dispatch --check-role` 可对候选做关键词软校验）。

拓扑：用户为根，派发边深度 = 1 截断，全局无环（DAG），杜绝 A→B→A 循环转包。设计权衡与「激活派发 / 转派被拒」两段示意见 `docs/design.md`。

## 任务包生命周期

`dispatch/tasks/*.md` 是一次性票据：`dispatch/tasks/` 只留在途，完成后归档。

1. **生成**：文件名带任务 ID（`<项目>-<ID>-<slug>.md`），正文写 `- 目标项目：<别名>（<绝对路径>）`。
2. **在途**：派发后票据留在 `dispatch/tasks/`；`dispatch/log.md` 记录会话、状态与目标 HEAD。
3. **落地**：目标项目完成并本地 commit，账本归档到目标 `agent-workflow/tasks/<type>/done/<ID>.md`（目录式；旧 `done.md` 大文件由目标项目内 `awf status` 自动迁移）。
4. **归档**：完成后在调度方运行 `awf-dispatch --prune`（默认 dry-run，只打印计划），确认后加 `--apply` 把票据移到 `dispatch/archive/<目标别名>/<YYYY-MM>/<原文件名>`。

判定依据：目标仓库提交消息含任务 ID，**或** 目标账本 `tasks/<type>/done/`（目录式）已含该 ID（兼容旧 `done.md`）——提交消息没写 ID 的票据也能归档；解析不到目标项目/任务 ID、目标路径不存在或不是 git 仓库时判 unknown 并跳过（不猜）。

```sh
./agent-workflow/bin/awf-dispatch --prune           # dry-run：打印票据 / 目标 / 任务ID / 判定 / 将移往路径
./agent-workflow/bin/awf-dispatch --prune --apply   # 真正移动已完成票据
```

`dispatch/log.md` 是**永久派发日志**，`--prune` 只移动票据文件，不清理、不改写日志。

机械/可验证任务（升级、同步、拷贝）直接完成并提交，验证以复跑命令为准，不要为复核再派生子任务；复杂业务改动才需要独立复核。

## 派发生命周期（派发方账本 active → done）

派发动作纳入**派发方自己的任务账本**管理（不能只有 `dispatch/log.md` 一条流水）：派发前在派发方账本登记「进行中开发任务」作为**兜底锚点**，代理核验收讫后由派发方归档——**必有回报是主机制**，登记 active 只在会话失联时兜底，防止「派发了就忘记」。

- **回报规则总表（DISPATCH-145；统一并入 DISPATCH-133 必有回报 / DISPATCH-141 决策回派发端 / DISPATCH-143 远程办公 / DISPATCH-144 状态透明化）**——以下**必报点**任一触发，目标会话必须主动回报派发方（沿用「派发方 / 目标会话」表述；异步派发同样适用，mid-status 只覆盖 `--wait` 等待超时前；**适用于链条每一跳**，见下「转派链卡点必报」）：
  1 受理任务（会话打开）：已受理 + 对任务的理解一句话 + 计划/预计；
  2 开始执行（首个实质动作前）：开始实施 X，预计 Y；
  3 里程碑完成（如发版/批次派发/首批升级）：里程碑结果 + 下一步；
  4 状态转换（active→review / review→active 修复）：转换原因 + 结果 + 下一步；
  5 review 不通过：问题清单 + 修复计划 + 预计；
  6 修复开始 / 修复完成待复审：修复内容 / 待复审；
  7 复审（复验）通过 / 再次不通过：复审结果 + 结论；
  8 需用户确认/补充/决策：「阻塞：需用户确认 X（问题+选项+建议+解除条件）」——**不得在目标会话内向用户提问**（禁止 ask_user_question 等弹窗），由派发端转述用户、拿到决策后 `awf-dispatch --session <会话ID>` 续发，决策送达前**不得擅自执行推荐方案**（DISPATCH-141）；
  9 阻塞/依赖缺失/范围不清：阻塞点 + 原因 + 解除条件（含环节/错误/阻塞点），保持会话等待、不得静默停等（否则派发方误判失联，形成双向等待，如 2026-11-04 DEV-143 实证）；
  10 完成（最终）：状态 / 产物 / commit / 验证结果 / review 结论。
  11 空闲/收尾（DISPATCH-147 追加；无任务发生时也报平安）：必报点 10 完成后追加收尾句「任务完成，会话空闲，可续发（来源会话：<会话ID>）」；完成收尾后或等待外部已报阻塞后，会话仍存活但 >10 分钟无新必报点回报时发空闲心跳（空闲+仍在线+上次动作时间+无卡死声明），间隔 ≥10 分钟或仅在有活动变化时；非任务动作（bootstrap 校验/通道自检/仓库体检）可选发「自检状态」回报（细则见下）。
- **回报时机（定死）**：① 任一必报点触发后**一回合内**必须回报，不许拖到下一步；② 执行中途长时间无里程碑时，**每 5-10 分钟回报一次中途状态**（当前在做 X / 已完成 Y / 预计 Z / 未卡死声明），杜绝「闷头做完才报」——不因「还在修复 / 还没最终成功」而沉默；③ 等待外部（派发方/用户）时回报「阻塞等待中」+ 已等时长，不静默。
- **回报字段（固定，一项不能少）**：当前状态（哪个必报点 / 任务状态字段 active/review/blocked…）+ 执行内容（完成的工作、成功与否）+ 下一步（将做什么）+ 预计（时间 / 是否等待外部）+（如适用）commit / 验证结果 / review 结论。
- **违约后果（定死）**：不按必报点回报 / 超时无中途状态 → 派发方按「疑似失联」处理：主动追问（`awf-dispatch --session` 发「状态在哪里？按必报点回报」）→ 追问无果登记滞留 → 上报用户决定重派/干预；「完成才报、中途全沉默」视为违约，review 时连坐；派发方同样被约束：收到回报必须核验 + 转达用户（如适用）+ 归档，不许只轮询不读会话。
- **转派链卡点必报（DISPATCH-145 追加；回报链跟随派发链）**：框架支持再次转发（多层转派：A 派 B、B 再转派 C，DEV-128），必报点总表对**链条上每一跳**都适用（C 报 B、B 报 A、最终汇到源头派发方/用户），不是只有最后完成才报。
  - **转派不断链**：转派方（B）收到 C 的卡点/完成回报后**必须继续向上游 A 汇报状态**（「已转派 C 处理，C 回报 X」），汇聚职责不消失；转派后 A 仍对该任务负责（跟进/追问/兜底），不能认为「转出去就与我无关」。
  - **卡点必报**：卡点 = 阻塞（依赖缺失/外部输入/范围不清/需确认/工具失效/冲突待决/进程等待）——一旦进入等待，立即按必报点表回报上游：卡点类型 + 原因 + 已尝试 + 解除条件 + 预计。
  - **不静默铁律**：卡点/等待态不允许只在会话内等待，必须发出回报消息，即使没有新进展也按 **≤5 分钟**间隔发「仍阻塞」心跳。
  - **静默等待 = 违规**：卡点不回报 / 静默等待超过约定心跳 = 违规，记入任务账本，派发方按「疑似失联」升级（追踪 → 汇报 → 必要时上报用户决定重派 / 处分记档）。
  - 需用户确认（DISPATCH-141）/ 远程办公（DISPATCH-143）在转派链中：卡点上抛到需要用户决策的层级，该层负责沿派发链汇到用户（最终统一经 IM 送达用户，符合 CONVENTION.md 决策汇聚）。
- **远程办公状态判定（DISPATCH-143 定义升级：熄屏＝远程办公，非「离线」）**：需用户确认前先跑 `awf-dispatch --screen-state`（macOS：CoreGraphics 锁屏 + `pmset -g log` 最近 Display 事件；失败保守返回 unknown）。`off`/`locked`＝远程办公状态（remote，用户不在电脑前、经 IM 在线随时可决策）→ 照常回报「阻塞：需用户确认 X」并注明「远程办公状态（remote），请派发端经 IM（飞书）通知用户决策」，保持等待不擅自决策；`on`（亮屏，用户在电脑前）→ 原 DISPATCH-141 路径；`unknown` → 回报注明由派发端酌情。派发端收到「远程办公状态」标记 → **立即、主动**经 IM 通知用户决策或置待决队列（防遗忘锚点），用户决策后 `--session` 续发——远程办公路径是正常就绪流程的一部分，不存在「等待用户回来」。
- **状态透明化（DISPATCH-144）**（并入总表）：中间状态转换（review 不通过 / 修复开始 / 修复完成待复审 / 复审通过或再次不通过 / 归档完成 + 最终回报）均落上述必报点 4-7/10；回报时机不得晚于状态转换后一回合内，异步派发同样适用（mid-status 只覆盖 `--wait` 等待超时前）；派发方按远程办公状态（remote，DISPATCH-143）判定是否经 IM 主动通知用户。
- **回报投递通道（DISPATCH-146）**：本任务的回报经通道投递派发方，非仅写会话回复文本——目标会话在任一必报点（1-10）/中途状态回报时运行 `awf-dispatch --report --to <派发方会话ID> "<回报文本>"`（派发方会话 = 派发方运行 awf-dispatch 时所在会话环境，自动捕获并随注入文本告知目标；`--from` 默认取当前会话，`--ticket` 可带派发单号），命令把「回报投递」消息**推送进派发方会话收件箱（inbox）并触发其回合处理**，派发方无需轮询即可收到（含时间戳/来源会话/派发单）；RPC 不可达（界面未运行 / 无凭证 / 未注入派发方会话）时自动降级写入收件箱文件 `dispatch/reports/inbox/<来源会话ID>.md`（派发方可查）。10 必报点 + 转派链每一跳 + mid-status 全程适用；回报内容仍按必报点表组织（说什么不变，通道负责怎么送达）。派发方收回报后仍按既有职责核验 + 转达用户（如适用）+ 归档，按远程办公状态（remote，DISPATCH-143）判定是否经 IM 主动通知用户。机制细节（捕获/降级/互斥）见 `docs/dispatch.md` 与技能层。
- **空闲/收尾/自检（DISPATCH-147 追加；无任务发生时也报平安，杜绝「有会话在动却不知在干嘛」）**：复用 `awf-dispatch --report` 通道投递派发方，不新造通道。a 收尾报平安：必报点 10 完成回报后追加收尾句「任务完成，会话空闲，可续发（来源会话：<会话ID>）」，不再默默安静结束；b 空闲心跳（防「卡住」误判）：任务完成收尾后 / 等待外部但已报过阻塞后，会话仍存活且距上次回报 >10 分钟无新必报点回报时，主动回报「空闲心跳：空闲+仍在线+上次动作时间+无卡死声明」，此后每 ≥10 分钟一次或仅在有活动变化时；**防刷屏**：心跳与已报过的最后状态合并（无新进展不重复整段，只声明「仍空闲在线」），与执行中的 5-10 分钟中途状态错峰不叠加；阻塞态按转派链「仍阻塞」心跳 ≤5 分钟优先，空闲心跳仅在其缺席时兜底；c 自检/自测透明：非任务动作（bootstrap 校验/通道自检/仓库体检）可选发「自检状态」回报（做了 X / 结果 OK），不强制、不打断任务主线，多动作可合并一条，自检不计入也不替代空闲心跳（空闲心跳是必定义务）。与静默=违规（既有违约条款）衔接：正常空闲与静默等待/失联的区别 = 空闲心跳是否发出——**空闲也要报**；无心跳且无回报 → 派发方按既有「疑似失联」流程处理不变。机制细节（投递/降级）复用 DISPATCH-146 通道，见 `docs/dispatch.md` 与技能层。
- **转达用户回执格式（DISPATCH-152 追加；派发方 → 用户）**：派发方收回报并核验后**转达给用户时按固定回执格式**（不再各自发挥）；状态符号随任务状态切换 ✅ 完成 / ❌ 失败·核验不过 / ⏳ 阻塞进行中；模板字段：发送者（回报投递头的 项目/会话ID/派发单/时间）+ 执行内容（=回报字段措辞，DISPATCH-158）+ 改动范围 + 验证（含「我独立重跑确认」）+ 问题/风险（无则"无。"+一句解释）+ 我的处理（核验 commit/产物 + 已归档 done + 前置问题处理，以「无需你操作」收尾）。完整可照抄样例与三态用法见 `docs/dispatch.md`「转达用户回执格式」小节。
- **回报正文排版（DISPATCH-153 追加）**：回报正文用 markdown 结构化，**禁止整段长文本**（实测 ①②③④ 连段可读性差，用户 2026-11-05 要求美化）——固定骨架（可照抄，任何必报点通用）：

  ```text
  ## ✅ 完成回报（<任务编号> · <一句话任务名>）

  - **状态**：done（已归档）/ active / blocked…
  - **执行内容**：<做了什么、成功与否，1-2 句>
  - **改动范围**：<文件/产物分类列点，带量化>
  - **commit**：`<短号>`（未 push）
  - **验证**：<check/构建/签名 一行证据>
  - **遗留/风险**：<有则列点；无则"无。">

  任务完成，会话空闲，可续发（来源会话：<会话ID>）
  ```

  受理 / 开始执行 / 中途状态 / 阻塞 同骨架，标题换状态词与符号（如「⏳ 阻塞进行中（<编号> · <任务名>）」），字段按「回报字段（固定）」表（DISPATCH-145）；收尾句（DISPATCH-147）保留在正文末尾。

- **登记（派发前，兜底锚点）**：创建 active 任务，字段含 目标 worker（目标项目）/ 关联票据（`dispatch/tasks/<票据>`、派发时间）/ 一句话目标 / 验收标准。
- **归档（核验后）**：目标 agent 回报后**派发方核验收讫**才归档 done（补 完成日期 / 结果概要 / commit 引用），并按惯例写 `dispatch/log.md` 流水。
- **无回报仅当会话失联**：唯一没有回报的情形是会话确实失联（进程退出 / 会话关闭）；此时登记 active 兜底，派发方例行扫描账本发现滞留 → 追问代理状态 / 重派 / 上报用户决策。归档 done 不是代理单方面的动作。

## 执行：会话优先

有派发器时用 `awf-dispatch`（**默认异步**：创建会话并发送任务后立即返回会话 ID，不阻塞调度方）：

```sh
./agent-workflow/bin/awf-dispatch <别名|目录> dispatch/tasks/<ID>-<slug>.md
```

它会：

1. 跑 G1–G4 前置检查（G2 读本 harness 的工作区清单，G4 检查会话服务地址与本地认证）
2. 默认复用目标工作区里同项目同模块的常驻会话（没有才新建）
3. 发送任务包后立即返回；加 `--wait` 才等待回合结束并确认落地（`--timeout` 同时约束两端）
4. 记日志：未等待时状态为「已发送，未等待回合」，并写明如何回到该会话继续
5. 打印会话信息；**后续细节由用户在同一个会话里继续提**

复用目标工作区已有会话可减少会话数量；没有可复用的会话时再新建。同一项目同一模块的后续任务建议继续用同一个会话，不同模块各自一个会话。

**全局会话上限（DEV-183，按项目可配）**：所有项目合计的 `[awf]` 派发会话总数上限，默认 3（`DEFAULT_MAX_GLOBAL_AWF_SESSIONS`）。**每个项目可各自设置不同上限**：项目专属环境变量 `AWF_MAX_SESSIONS_<项目ID>`（项目ID = 目标目录名，大写、`-`→`_`，如 `AWF_MAX_SESSIONS_UXRSAMPLE=5`）> 通用 `AWF_MAX_SESSIONS` > 默认 3。复用空闲会话不受此限（复用不新增会话）；需要新建且已达上限时报错，须等待现有会话空闲（`--queue-timeout`）或清理归档后重试，`--force` 为逃生口。

需要本次回合结果时显式等待：

```sh
./agent-workflow/bin/awf-dispatch <别名|目录> dispatch/tasks/<ID>-<slug>.md --wait --timeout 900
```

> 默认不等待时，调度方只确认「任务已发送」；目标 agent 的最终回报稍后回到图形界面会话查看，日志里记有会话 ID 与打开方式。`--no-wait` 是默认行为的兼容别名（与 `--wait` 互斥）。

> **派发不建团队承载**（DEV-138）：派发动作即启动目标工作区的子代理会话，不需要 captain/dispatcher 成员层；多目标并行 = 多次派发（默认异步互不阻塞），需要某回合结果时在主会话分别加 `--wait`（`--timeout` 限时）等待并确认落地，或稍后回到各会话查看回报。

手工等价操作：图形界面左侧切到目标工作区 → 新建会话 → 粘贴任务包。效果相同，只是没有自动前置检查与日志。

### 可选：`--team`（团队拆分建议）

给派发命令加 `--team` 时，任务包末尾会追加一段「可选：用团队执行」建议：目标 agent 可先拆 2–3 个可并行子任务、声明依赖，再由队长汇总；团队协作插件不可用时忽略该节，按普通会话完成即可。拆分不改变验收标准，账本仍只由一个 Owner 写入。该参数只影响会话模式注入的任务包，`--handoff` 交接单保持原文；不加时任务包与旧版一致。

```sh
./agent-workflow/bin/awf-dispatch <别名|目录> dispatch/tasks/<ID>-<slug>.md --team
```

## 回退

| 情况 | 回退 | 代价 |
|---|---|---|
| 会话服务未运行 / 认证失效 | 派发器无人值守模式（需用户同意；具体命令见派发器文档与派发技能） | 默认后台启动并立即返回输出路径（`--wait` 才同步等待）；会话不在工作区列表，用户不能直接续聊 |
| 无法创建会话 | `awf-dispatch --handoff` | 只生成交接单，需用户手工在目标会话执行 |
| 目标未登记工作区 | `--add-workspace` 或图形界面添加 | 否则会话落在未分组会话，用户找不到 |
| 目标无工作流 | 先 `awf init`，再派发 | 不要跳过 G1 |

## 写者与账本

- 目标 agent 写目标项目的 `tasks/**`、`status.md`、代码与 commit。
- 调度方只写自己的 `dispatch/log.md` 与任务文件；**不要**跨仓库改目标账本。
- **团队不承载跨仓库任务**：派发即启动目标工作区的子代理会话，写入一律由目标项目自己的工作区会话完成；团队只保留本工作区内的并行拆分用途。
- 一个任务只有一个 Owner；目标已有 active 任务时不要并行派发同一模块。

## 验收与收尾

1. 回合结束后检查目标 agent 的回报是否包含任务包五项（状态 / 变更文件 / 验证结果 / commit / 阻塞）。
2. 在目标仓库核对 `git log -1`、`git status`、`./agent-workflow/check_workflow.sh`。
3. 调度方记录：会话 ID、任务文件、状态、目标 HEAD、时间；`dispatch/` 随调度方仓库本地 commit。
4. 用户后续细节优先回到同一会话；只有新目标或新任务才重新派发。

> 派发活动不写入目标项目账本；调度方的 `awf status` 只反映自身登记的任务，需在收尾时补跑一次。

> 目标 harness 若支持团队协作，任务包会附拆分建议；是否拆队由目标方自行决定，调度方不代开团队。

## 失败处理

- `source-forbidden`：票据头部标记「来源：工作流」被再次派发——`awf-dispatch` 只非阻塞提示核对转派理由并更新「路由裁决」（DEV-128 已放开，不再 FAIL）；需要改写原票据来源时由用户创建「来源：用户」的新票据。
- `workspace-missing`：通过 harness 的工作区管理添加，或使用 `--add-workspace`；不要用不相关目录参数绕过。
- `workflow-missing`：先 `awf init` / 补齐 `agent-workflow/`。
- `writer-held` / `session/conflict`：目标会话被占用或同目录写者冲突；切走/等待后重试。
- `auth-required` / `connection refused`：重开会话服务地址；或派发器无人值守模式（需用户同意，具体命令见派发器文档）。
- 回合超时：会话保留，不要杀掉；在图形界面查看进度。默认派发本身不等待（`--no-wait` 是默认行为的兼容别名），需要重派时直接重新派发并加 `--force`。

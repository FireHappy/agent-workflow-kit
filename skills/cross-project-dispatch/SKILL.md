# 跨项目派发

把任务交给目标项目自己的 agent，在**目标项目的工作区会话**中执行；调度方只发任务、收结果，不跨仓库改账本。

配套规范：目标项目的 `agent-workflow/workflows/cross-project.md`（kit 的 `templates/workflows/cross-project.md`）。

## 四道前置门（缺一不可）

| 门 | 检查 | 不满足时 |
|---|---|---|
| G1 工作流 | 目标有 `AGENTS.md`、`agent-workflow/project.yaml`、`workflows/`、`check_workflow.sh` | 先 `awf init`（需用户确认），不要向无流程仓库派发；仅「status.md 已过期」瞬态 warn 放行 |
| G2 工作区 | 目标路径已登记为当前 harness 的工作区（DSH：GUI 工作区列表 / `workspace.json`） | 在 GUI「添加工作区」，或 `awf-dispatch --add-workspace`；否则 handoff |
| G3 可写 | 目标无已跟踪改动、无其他 active 任务 | `--allow-dirty=tasks` 只豁免账本自我生成物（status/README/log）；active 冲突三选项：等它完 / `--allow-active` / `--new` |
| G4 通道 | 目标工作区能创建会话（GUI 在线、认证有效、模型可用） | 回退 headless（需用户同意）或 handoff |

只读任务可以放宽 G3，但仍建议在会话中执行，留下可追问的记录。

## 派发三规则（默认异步 / 派发即子代理 / 票据瘦身）

跨项目派发的动作与边界固定为三条规则（DEV-132），调度方（主线 / router）直接照此执行：

1. **默认异步派发**：只做「复用或新建目标工作区会话 → 发送任务包 → 记日志」，立即返回会话 ID，**主会话不被钉住**；需要本回合结果/落地确认时调用方**显式加 `--wait`**（配 `--timeout`）。
2. **派发即启动子代理**：派发动作的实质就是在目标工作区**启动一个子代理会话**，由目标 agent 独立完成并回报；**不启用智能体团队承载派发**——没有 captain / dispatcher 成员层；多目标就多次 `awf-dispatch`（默认异步互不阻塞），需要结果时各自 `--wait` 或回到会话查看。
3. **票据瘦身 + 分析归 worker**：router 只写 用户意图 / 硬约束 / 验收标准 / 路由裁决，**不写执行步骤、不做前置侦察**；前置分析由目标 worker 在自己的会话里用目标仓库 `tools/` 手册与 `memory/history` 完成，有疑问**返回 router / 用户决策**。

### 调度方最小操作序列

1. 预检（不建会话）：`awf-dispatch <目标> <票据> --dry-run`，确认 G1–G4
2. 写票据 `dispatch/tasks/<项目>-<ID>-<slug>.md`（见下「任务包」：只含 意图 / 硬约束 / 验收标准 / 路由裁决）
3. 派发：`awf-dispatch <目标> <票据>`（默认异步，立即返回会话 ID，主会话继续做其它事）
4. 需要本回合结果/落地确认时显式加 `--wait --timeout 900`；不加时稍后回到图形界面会话查看目标 agent 的任务包五项回报
5. 收尾：写 `dispatch/log.md` → 更新本仓库账本 → `--prune` 归档票据 → 本地 commit
6. 有依赖的目标等上游回报「成功 + commit 已落地」后再派；失败/超时按 `--wait` 退出码决定重试、改派或降级
7. worker 回报「阻塞：需用户确认 X」时（DISPATCH-141）：由你（router）转述用户、拿到决策后 `awf-dispatch <目标> <票据> --session <会话ID>` 续发决策给 worker（worker 不在目标会话内提问、决策送达前不擅自行事）。回报带「远程办公状态（remote）」标记（DISPATCH-143 定义升级，worker 用 `awf-dispatch --screen-state` 判出 off/locked；熄屏＝远程办公状态：用户不在电脑前、但经 IM 在线随时可决策，不是「离线」）→ **立即、主动**经 IM（飞书小迪司）通知用户决策或置待决队列（派发方账本登记防遗忘），用户远程决策后转述续发——这是远程办公正常流程的一部分，不等用户回电脑前
8. **状态透明化（DISPATCH-144）**：worker 在 dev 流程中间状态转换（review 不通过 / 修复开始 / 修复完成待复审 / 复审通过或再次不通过 / 归档完成）时**主动回报你**（当前状态 / 结果 / 下一步 / 预计，时机不晚于状态转换后一回合，异步派发同样适用）；收到这类进度回报 → 转达用户（按 remote 判定是否经 IM 主动通知），不要等 worker 最终成功才知会。

### 脚本做了什么

脚本会（**默认异步**，`--wait` 是显式开关，不是默认动作）：

1. 跑 G1–G4，并打印前置换结果；
2. **默认按「项目 + 模块」复用**目标工作区里的常驻会话（标题精确等于 `[awf] <项目> · <模块>`），不每次新建；没有匹配到本模块会话时才新建，标题同样用规范格式；
3. 发送任务包后立即返回会话 ID；加 `--wait` 才轮询到回合结束并确认落地（`--timeout` 同时约束回合等待与落地等待）；
4. 把 sessionId、标题、模块、会话来源（复用/新建）、状态、目标 HEAD 写到 `dispatch/log.md`；未等待时状态为「已发送，未等待回合」，并写明回到 GUI 会话的方式；
5. 打印会话信息；后续细节由用户在同一个会话里继续提。

**默认复用，不每次新建**：同一项目同一模块的后续任务继续用同一个会话，会话上下文就是开发资产；不同模块各自一个会话，不借其它模块的上下文。派发器不看上下文压力（压缩由 harness 负责）；选中的会话正在运行时先进等待队列（`--queue-timeout`，默认 180s），超时前回报**中途状态**（已等秒数/目标 HEAD/会话产出）不静默超时，之后报错并建议 `--new`，不会静默改成新建。压力 ≥ 0.9 只提示「可考虑 `--new`」，不自动切换。只有并行独立需求、上下文污染、排障或模块隔离时才加 `--new`。

会话命名与模块：

- 标题固定为 `[awf] <项目名> · <模块名>`，不带任务号；同一模块的多个任务共享一个会话。
- 模块来源：`--module <名称>` > 票据可选行 `- 模块：<名称>` > 默认 `通用`。
- 复用键 = 项目 + 模块：标题不同（其它模块）不复用，直接新建本模块会话。项目里还没有规范会话时，旧格式（无 `[awf]` 标记，形如 `<项目> · <任务>`）空闲会话**默认不迁移**——只有两种情况下复用它并改名为规范标题：① 该会话消息里含派发任务包标记（旧版派发器在它里面派发过）；② 显式加 `--allow-legacy-reuse`（用户确认）。用户自建的 `<项目> · xxx` 普通会话既无标记也无显式放行，不会被复用/改名/注入任务；其余情况不猜，直接新建。

常用参数：

| 参数 | 作用 |
|---|---|
| `--wait` | 等待回合结束**并确认落地**（目标 commit 或账本归档）；**显式开关，脚本默认不等待** |
| `--timeout N` | 回合等待 + 落地等待的总秒数，仅 `--wait` 生效（默认 600） |
| `--no-wait` | 默认行为的兼容别名，与 `--wait` 互斥 |
| `--reuse` | 默认行为：按「项目 + 模块」复用目标工作区已有的常驻会话 |
| `--new` | 强制新建会话（隔离/调试）；与 `--reuse` 互斥 |
| `--allow-legacy-reuse` | 显式放行旧格式（无 `[awf]` 标记）空闲会话迁移复用并改名；默认只在会话消息含派发任务包标记时自动迁移，用户自建会话不会被吞 |
| `--module <名称>` | 模块名（标题 `[awf] <项目> · <模块>`）；默认取票据「模块：」行，都没有用「通用」 |
| `--session <id>` | 直接向指定会话发送（续跑历史会话/人工指定），不会新建 |
| `--queue-timeout N` | 选中会话繁忙时的队列等待上限秒数（默认 180；超时前回报中途状态） |
| `--dry-run` | 只做前置检查，不创建会话 |
| `--headless` | 回退 headless（默认后台启动，`--wait` 才同步等待） |
| `--handoff` | 只生成交接单，不执行 |
| `--add-workspace` | 目标未登记工作区时自动登记 |
| `--team` | 任务包附加团队拆分建议，目标方自行决定是否拆队 |
| `--prune` | 归档已完成票据：扫描 `dispatch/tasks/*.md`，按目标 commit / 账本 `done.md` 判定；默认 dry-run 只打印计划 |
| `--apply` | 配合 `--prune` 真正移动文件到 `dispatch/archive/<别名>/<YYYY-MM>/` |
| `--json` | 机器可读输出（含 `reused: true/false` 与 sessionId） |

`--headless` 默认也在后台启动并立即返回输出文件路径，`--wait` 才同步等待；headless / handoff 不参与会话复用。

手工等价操作：GUI 左侧切到目标工作区 → 打开（或新建）会话 → 粘贴任务包。效果相同，只是没有自动前置检查与日志。

## 票据生命周期

`dispatch/tasks/*.md` 是一次性票据：完成后用 `--prune` 归档到 `dispatch/archive/<别名>/<YYYY-MM>/`，主目录只留在途；`dispatch/log.md` 是永久日志，不清理。

判定 completed：目标仓库提交消息含任务 ID，或目标账本 `agent-workflow/tasks/*/done.md` 已含该 ID；解析不到目标项目/任务 ID、目标不是 git 仓库时判 unknown 并跳过。

```sh
"$KIT/bin/awf-dispatch" --prune           # dry-run：只打印计划，不改文件
"$KIT/bin/awf-dispatch" --prune --apply   # 确认后真正归档
```

## 任务包（票据瘦身：意图 / 硬约束 / 验收标准 / 路由裁决）

派发前写一份任务文件（`dispatch/tasks/<ID>-<slug>.md`），**只含四类信息**：

- **用户意图**：`任务：<ID> <一句话目标>`；`- 来源：用户 | 工作流`（缺省=用户；来源=工作流允许按需继续转派，DEV-128）
- **路由裁决**：`- 路由裁决：目标=<别名> / 通道=awf-dispatch / 理由=<role 匹配说明>`
- **硬约束**：目标项目与任务 ID；类型 `dev|debug|docs`；可选模块 `- 模块：<名称>`（同一项目不同模块各自一个常驻会话；不写默认「通用」）；修改范围、明确不做什么；提交要求（只允许本地 commit，禁止 push）；**分析归属**（前置分析在本会话内用目标仓库 `tools/` 手册与 `memory/history` 完成，有疑问返回决策）
- **验收标准**：逐条可勾选，含**必须实际执行**的验证命令；回报格式（任务包五项）：状态 / 变更文件 / 验证结果 / commit / 阻塞

**不写执行步骤、不做前置侦察**：router 不替目标 worker 做 build_guide / 历史产物 / 场景清单等；目标 agent 用自己的会话与目标仓库的 `tools/` 手册、`memory/history` 完成分析。

任务包不要依赖调度方上下文；目标 agent 是独立会话。

## 回退

回退由调度方决定并执行；不在派发链路里设 dispatcher 成员层：

| 情况 | 回退 | 代价 |
|---|---|---|
| GUI 未运行 / 认证失效 | `--headless`（需用户同意） | 默认后台启动并立即返回输出路径（`--wait` 才同步等待）；会话不在 GUI 工作区，用户不能直接续聊 |
| 无法创建会话 | `--handoff` | 只生成交接单，需用户手工在目标会话执行 |
| 目标未登记工作区 | `--add-workspace` 或 GUI 添加 | 否则会话落在 Ungrouped |
| 目标无工作流 | 先 `awf init`，再派发 | 不要跳过 G1 |

## 写者与账本

- 目标 agent 写目标项目的 `tasks/**`、`status.md`、代码与 commit。
- 调度方只写自己的 `dispatch/log.md` 与任务文件；**不要**跨仓库改目标账本。
- 账本与 commit 归主线（调度方）；目标项目账本由目标 agent 写，派发者不代写。
- 一个任务只有一个 Owner；目标已有 active 任务时不要并行派发同一模块。

## 验收与收尾

1. `--wait` 等回合结束后，检查目标 agent 的回报是否包含任务包五项（状态 / 变更文件 / 验证结果 / commit / 阻塞，见目标项目 `cross-project.md`）。
2. 调度方在目标仓库核对 `git log -1`、`git status`、`./agent-workflow/check_workflow.sh`（关键命令不只看目标 agent 自述）。
3. 调度方记录：会话 ID、任务文件、状态、目标 HEAD、时间。
4. 用户后续细节优先回到同一会话；只有新目标或新任务才重新派发。

## 僵尸会话与无进展

复用旧会话时可能遇到「僵尸会话」：回合 16–21ms 即时结束，零 assistant 输出、零工具调用，但脚本会一直等到 `--timeout`。派发器对 `--wait` 增加两类可靠性判定：

1. **无进展快失败（退出码 4）**：回合耗时 <5s 且零输出、零工具调用 → 立即返回 4，文案「会话疑似僵尸（回合即时结束且零输出），请用 --new 重派或在 GUI 重开会话」。`--json` 的 `zombie`、`turnSeconds`、`sessionId` 与日志状态都会标明。
2. **等落地（回合结束 ≠ 完成）**：正常回合结束后每 10s 检查目标仓库——以任务发送前一刻的初始 HEAD 为基线，`git rev-parse HEAD` 变化且 `initial..HEAD` 区间内**任一 commit（提交消息）含本任务 ID**（任务 commit 被无关 commit 压顶仍算落地），或账本 `agent-workflow/tasks/<type>/done.md` 出现任务 ID（归档）；只有无关 commit 不算落地。超时返回 3，状态「回合已结束但任务未落地」，不要当成功。可重新派发（同名 `--force`）或 `--session` 续跑。headless 模式：进程非零退出为**执行失败，返回独立退出码 5**（不是 3 的超时/未落地）；退出 0 后仍按上述落地校验。

僵尸判定优先于落地：不要在僵尸会话上继续空等；先 `--new`（或 GUI 重开），再按正常流程验证。

## 失败处理

- `workspace-missing`：在 GUI 添加工作区，或 `--add-workspace`；不要用 `cwd` 绕过。
- `workflow-missing`：先 `awf init` / 补齐 `agent-workflow/`。
- `writer-held` / `session/conflict`：目标会话被 GUI 占用或同目录写者冲突；切走/等待后重试。
- `auth-required` / `connection refused`：重开 GUI URL；或 `--headless`。
- 回合超时或未落地（退出码 3）：会话保留，不要杀掉；回 GUI 看进度，由调度方决定加大 `--timeout` 重派（`--force`）、`--session` 续跑、改派或降级。
- 疑似僵尸会话（退出码 4）：用 `--new` 重派或在 GUI 重开会话，不要继续续跑同一会话。
- headless 进程非零退出（退出码 5）：执行失败，不是超时/未落地；按 `dispatch/headless/*.log` 排查目标侧错误后重派。

## 安全

`awf-dispatch` 只在本地读取 DSH GUI 的认证 cookie，用于本机 API；不打印、不写入任务文件或日志。不要把 cookie 粘进任何输出。

# 转派链卡点必报：回报链跟随派发链、卡点上抛、静默=违规（DISPATCH-145 追加之二，DEV-155）

日期：2026-11-05。用户指示：「框架支持再次转发（多层转派），不是固定的主-子两级；但每次任务的问题卡点回报是必须的，不能让有些 worker 卡住问题却不发出消息、就在自己会话里等待——现实职场这样要受处分的。」要求：回报规则与层级无关，链上任意一层卡住必须上抛消息，静默等待=违规且写明处置语义。

## 机制（写入必报点总表之后，作为 DISPATCH-145 追加小节）

1. **回报链跟随派发链**：A 派 B、B 再转派 C（DEV-128 允许继续转派）→ C 对 B 负责、B 对 A 负责，回报义务沿派发链逐级上抛，最终到源头派发方/用户；必报点总表（10 点）对**链条上每一跳**都适用，不是只有最后完成才报。
2. **转派不断链**：转派方 B 收到 C 的卡点/完成回报后**必须继续向上游 A 汇报状态**（「已转派 C 处理，C 回报 X」），汇聚职责不消失；转派后 A 仍对该任务负责（跟进/追问/兜底），不能「转出去就与我无关」。
3. **卡点必报**：卡点 = 阻塞（依赖缺失/外部输入/范围不清/需确认/工具失效/冲突待决/进程等待）——一旦进入等待，立即按必报点表回报上游：卡点类型 + 原因 + 已尝试 + 解除条件 + 预计。
4. **不静默铁律**：卡点/等待态不允许只在会话内等待，必须发出回报消息，即使没有新进展也按 **≤5 分钟**间隔发「仍阻塞」心跳。
5. **静默等待 = 违规**（不是建议、是处置）：卡点不回报/静默等待超心跳 = 违规，记入任务账本；派发方按「疑似失联」升级（追踪 → 汇报 → 必要时上报用户决定重派/处分记档）。
6. **141/143 衔接**：需用户确认/远程办公在转派链中，卡点上抛到需要用户决策的层级，该层负责沿派发链汇到用户（最终统一经 IM 送达，符合 CONVENTION.md 决策汇聚）。

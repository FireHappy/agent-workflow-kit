# agent-workflow · 团队执行（技能）

> 由 agent-workflow-scaffold 主技能路由加载（AGENTS.md 开工顺序按任务类型强制加载本技能）。
> 团队任务和 awf 账本是两套状态，必须显式对齐（先登记、再建队）。

## 团队协作（可选）

目标 harness 支持多角色/多会话时，可按三条轨道组织团队（docs / dev / debug）；完整流程见下节。`awf-dispatch --team` 可在任务包尾部附加拆分建议，插件不可用时自动降级为普通会话。本技能不依赖任何团队插件，本节只在目标 harness 具备该能力时生效。

> 本文件随 `agent-workflow-scaffold` 技能分发（仓库根即技能目录），但不进入 `templates/`、不随 `awf init` 写进每个新项目——由使用方按需采用。
> 主规范仍是 `agent-workflow/README.md` 与 `agent-workflow/workflows/*.md`；本文件只规定"什么时候、怎么把主线流程交给团队"。
> 三条轨道直接对应 `workflows/docs.md`、`workflows/dev.md`、`workflows/debug.md`，不另立规范。

## 0. 与账本的关系：先登记，再建队

团队任务和 awf 账本是两套状态，必须显式对齐：

1. **建队前**把主任务写进 `agent-workflow/tasks/<type>/current.md`：`Owner=队长`、`协作模式=team`、`来源任务=<团队名>`
2. 团队名用 `<任务ID>-<slug>`（如 `<任务ID>-team-flow`），归档后能按 ID 检索
3. 成员**不写** `tasks/**`；只报告改动文件、命令输出、目标 HEAD
4. 收尾时由队长把团队产出写进账本并归档：**归档 → check → awf status → commit**；归档前按「收工三步」补完最后一条 `awf log`（改正文 → 记一条 → 回读末行；执行记录只由 awf 追加，禁止手改）
5. `.agent-teams/` 不入库；对账依据是 `dispatch/log.md` + 账本 + `git log`

这一步是原来最大的缺口：团队"完成"很容易，账本里却查不到对应记录。

## 1. 什么时候用

- 多文件、跨模块、需要独立复核的改动
- 诊断类问题有 2 个以上可并行验证的假设
- 文档要作为后续开发的契约（先 docs 后 dev）

**不用**：一句话文案、单文件小修、纯查询、跑一次校验。为这类任务开团队，协调成本大于收益。

## 2. 三条轨道

### 轨道 A：docs（文档 / 契约）

适用 `workflows/docs.md`。

```text
docs（撰写）
  └─> docs-review（事实核对：代码路径、链接、过期信息）
        └─> archive（队长归档 + 提交）
```

- 成员：`doc-writer` + `fact-checker`（1 人可完成时不开队）
- 硬性要求：结论必须给 `file:line`；不确定标「待确认」；审阅必须实际打开被引用的文件
- 账本：`tasks/docs/`，ID `DOCS-xxx`

### 轨道 B：dev（功能开发，默认主力）

适用 `workflows/dev.md`（review 子流程见 `workflows/review.md`）。

```text
docs（设计/契约，可裁剪）
  └─> dev（实现，不 commit）
        └─> review-test（独立复核 + 独立重跑验证）
              └─> archive（文档回填 + 队长提交）
```

- 成员：`doc-writer`（可省）+ `implementer` + `reviewer`
- 硬性要求：实现只改声明范围；验证命令必须实际执行；review 必须独立重跑，禁止只读自我报告
- 账本：`tasks/dev/`，ID `DEV-xxx`

### 轨道 C：debug（缺陷 / 异常）

适用 `workflows/debug.md`。核心是假设可证伪，不是堆日志。

```text
hypothesis-a（假设 1 验证）┐
hypothesis-b（假设 2 验证）┤─> fix（根因修复 + 回归）
                          ┘        └─> verify（独立复核 + 回归范围确认）
                                        └─> archive（复盘入 history）
```

- 成员：`diagnoser` ×2（各自独立假设）+ `implementer` + `verifier`
- 硬性要求：每条假设写「假设 / 证据 / 证伪方法 / 结果」；根因未明确不得大范围改代码；verify 要跑**相关回归**而不只是原复现
- 账本：`tasks/debug/`，ID `DEBUG-xxx`

## 派发：跨项目（cross-project，不建队承载）

跨项目派发**不由团队承载**：派发动作的实质就是在主会话里执行 `awf-dispatch`，在目标项目工作区**启动一个子代理会话**，由目标 agent 按自己的 AGENTS.md 与工作流独立完成并回执。**没有 captain / dispatcher 成员层**；团队只保留本工作区内的并行拆分用途（§2 三轨）。多条派发轨道只决定「目标项目内部要不要拆」，本节只规定「谁派、谁等、谁汇总」——都是主线自己。

### 派发动作

1. 主线登记本仓库账本（`agent-workflow/tasks/<type>/current.md`，见 §0），写票据 `dispatch/tasks/<项目>-<ID>-<slug>.md`——**只含 用户意图 / 硬约束 / 验收标准 / 路由裁决**，不写执行步骤、不做前置侦察（模板见 `docs/dispatch.md` 任务包模板）
2. 主线执行 `awf-dispatch <目标> <票据>`：**默认异步**，创建/复用目标工作区会话、发送任务后立即返回会话 ID，**主会话不被钉住**
3. 需要本回合结果/落地确认时显式加 `--wait --timeout <秒>`；不加时稍后回到图形界面会话查看目标 agent 的任务包五项回执
4. 收尾：主线写 `dispatch/log.md`、更新本仓库账本、归档票据、本地 commit

### 多目标与依赖

- **多目标（无依赖，并行）**：多次 `awf-dispatch` 即并行（默认异步互不阻塞）；需要结果时调度方各自加 `--wait`，或稍后回到各会话查看；按回执到达顺序汇总。
- **有依赖**：上游回执「成功 + 目标 commit 已落地」后，主线才派下游；依赖关系写在主线的分解里，不写在票据里让目标方猜。

### 失败与超时

`--wait` 退出码供调度方（主线）决策：

| 退出码 | 含义 | 调度方处理 |
|---|---|---|
| 0 | 派发/等待正常结束（`--wait` 时回合已结束**且已落地**；**不代表任务成功**） | 按任务包五项核对目标回执，再进账本 |
| 2 | 前置门不过 / 派发失败（缺工作流、缺工作区、写者冲突、用法错误） | 按提示补门（`awf init` / `--add-workspace` / 等写者），或改派、降级 handoff |
| 3 | `--wait` 超时：回合未结束（会话仍在运行），或回合已结束但任务未落地（无 commit/未归档） | 不杀会话；回图形界面看进度，决定续等（重派并加大 `--timeout`；同名会话重派还需 `--force`）、`--session` 续跑或改派 |
| 4 | 疑似僵尸会话：回合 <5s 即时结束且零输出零工具调用 | 用 `--new` 重派或在图形界面重开会话；不要继续在同一会话上续跑空回合 |
| 5 | headless 进程非零退出（执行失败；独立于 3 的超时/未落地） | 按 headless 输出文件排查目标侧错误后重派 |
| 1 | 未预期异常 | 保留输出，原样回执；不静默重试 |

- 重试、改派、降级（无人值守 / handoff，具体命令与语义见 `docs/dispatch.md`）由调度方决定；无人值守需用户明确同意，不得自行降级。
- 目标回执「阻塞」时原样转述阻塞点，调度方不替目标改代码。
- 目标项目内部若有团队能力，是否拆队由**目标方**决定，本仓库不代开第二层团队。

### 豁免与成本

- 单行修改、只读查询、跑一次校验：直接做或直接派发，不建队（派发本身就不建队承载），回复里说明即可。
- 需要有人专门盯 `--wait` 回合结果的场景（无人值守 / CI）：可用后台任务或子代理执行 `awf-dispatch --wait`，但这只是把「等待」动作放到后台，不是「派发即建队」。

## 3. 质量合同：让插件当门禁

约定靠自觉，合同靠机制。非平凡改动优先用插件的 quality kind，而不是普通 work 任务：

| 用途 | 用法 |
|---|---|
| B 轨实现 | `kind=implementation`，把改动范围写 `inScope`、验证命令写 `verify`，验收写 `acceptance` |
| B/C 轨复核 | `kind=review`，`reviewedTaskId` 指回实现任务 |
| C 轨独立验证 | `kind=verification`，同样带 `verify` 命令 |

关键收益：**review 判 `needs_revision` 时，插件自动补 `repair` + 下一轮 review**，不要手工把 findings 变成新任务、更不要重排整条 DAG。手工补任务会丢掉 attempt 归属和重试计数。

纯文档、纯查询不要上 quality 合同——字段成本高于收益。

## 3.5 两级复核：速度与风险分级（默认走快速车道）

复核成本按改动风险分级，避免小改动也走满 review 循环：

| 轨道 | 适用 | 流程 | reviewer 轮 |
|---|---|---|---|
| **A 全量架构复核** | 架构级：工作流契约、AGENTS/模板结构、跨项目规则、命令默认行为、会话模型 | 实现（附 diff）→ review → 有 blocker 才 repair → 复审 | 完整（至多 1 次返工） |
| **B 快速车道（默认）** | 新增功能 / 小调整（新选项、bug fix、文档、机械任务） | 实现**必须自带测试进 smoke** + 自检门禁 → captain 快验（看 diff + 跑测试）→ 直接收尾 | 0 轮 |

### 快速车道的自检门禁（声称完成前必须贴输出）

```sh
bash test/smoke.sh            # 新增功能必须带新断言
python3 -m py_compile skills/cross-project-dispatch/scripts/awf-dispatch
bash -n bin/awf test/smoke.sh
./agent-workflow/check_workflow.sh
git diff --check
```

加上针对性 grep（如模板 harness 专有词）。grep 能查出来的问题不许到 reviewer 手里。

### A 类的复核要增量

- 实现者在任务回执里附 `git diff` 摘要 + 自检输出
- reviewer 看 diff 与关键门禁，不重读全部文档
- 返回 values：**只有 blocker/medium 影响正确性才 needs_revision**；low/措辞类记入「后续清单」，合并下次处理，不单独返工

### 测试归属：谁用谁的校验

| 场景 | 用谁的测试 | 含什么 |
|---|---|---|
| kit 自身开发（改 bin/awf、awf-dispatch、templates） | **kit 的 smoke + check_workflow** + py_compile/bash -n | 新功能必须自带断言进 smoke |
| 目标项目一般任务（升级框架/业务功能，经派发） | **目标项目自己的 check_workflow** + 任务包验收 + 目标自己的测试（如有单测） | **不跑 kit 的 smoke**——它是框架测试，与目标业务无关 |

> kit 冒烟测试只对 kit 开发负责；派发到别的项目时，以目标项目的校验为准。

> 判定依据是「框架测试套件能否兜底」：测试绿 + diff 合理 → B；涉及契约/默认行为/安全 → A。拿不准问用户。

## 4. 队长职责（三轨通用，不可下放）

1. 开工前登记账本（见 §0）
2. 建队前贴 3 行计划摘要（目标 / 轨道与成员 / 验收）；team 启动使用 `approval=automatic`（用户已授权），不再 staged 审批，发现方向错误立即叫停或改任务
3. 账本只由队长写；成员只报告
4. 收尾顺序固定：**归档 → `check_workflow.sh` → `awf status` → 本地 commit**
5. 成员"完成"不等于验收通过；关键命令队长自己复跑
6. 禁止 push
7. 团队终态后归档，不留悬空 attempt
8. 账本动作只由用户指令触发：**不主动建任务**；「删除」只认用户原话 + 二次确认；暂停 / 取消 / 结案不互相替代，含糊先反问（结案 = 完成归档，取消 = 作废归档并写明原因；完整触发表见 `skills/dev/SKILL.md`「人类授权纪律」）

## 5. 成本与约束

- 同一时间只开 **1 个团队**；成员 **2–3 人**
- 成员各自长上下文独立计费；并行的前提是真的有独立工作，不是"人多显得快"
- 建队前必贴 3 行计划摘要供用户核对；team 启动使用 `approval=automatic`（用户已授权）：跳过 staged 审批直接执行，发现方向错误可立即叫停或改任务
- 跨项目派发不建团队承载（见「派发」）：主线直接 `awf-dispatch` 启动目标工作区子代理会话（默认异步，需要本回合结果时显式 `--wait`）；目标方若有插件，是否拆队由**目标方**自行决定

## 6. 默认路由：先判目标仓库，再选通道

任务路由先回答「目标仓库是否 == 当前工作区」，**不要在选通道前默认建队**（与入口模板「任务路由」一致）：

1. **目标仓库 == 当前工作区**（本仓库任务）：
   - 小任务（单行修改、只读查询、跑一次校验）：单会话直接完成，回复里说明原因；
   - 可并行拆分（多模块、修改范围不重叠、共享写点明确、需要独立复核）：建队执行。
2. **目标仓库 ≠ 当前工作区**（跨仓库任务）：**默认 `awf-dispatch` 派到目标项目自己的工作区会话**；**团队不承载跨仓库任务**——成员会话工作区 = 建队方工作区，直接改目标仓库会越权或撞目标门禁（2026-11-01 教训：7 人团队在调度方工作区直接改 6 个项目仓库，任务归属凌乱、changedPaths 门禁卡死）。跨仓库任务不需要团队承载（派发即启动目标工作区子代理会话，见「派发」）；多目标=多次派发，等待由调度方在主会话显式 `--wait`。

需求进入后按此顺序处理：

1. **澄清**（只在需求有歧义时）→ 2. **贴 3 行计划摘要**（目标 / 轨道与成员 / 验收）→ 3. **自动建队并执行**（`approval=automatic`，用户已授权，跳过 staged 审批）→ 4. 成员后台执行
5. 主对话继续处理只读分析、跨项目派发、下一需求澄清 → 6. 报告回来后由队长汇总与验收

约束：

- 同一时间只开 1 个团队；新需求排队，不并行开第二个队
- 跳过条件：小任务（单行修改、只读查询、跑一次校验）、团队不可用、协调成本高于任务本身（建队开销大于任务）——直接做，并在回复里说明原因
- 本仓库内的建队使用 `approval=automatic`（用户已授权）：跳过 staged 审批直接执行；建队后仍贴 3 行计划摘要，发现方向错误立即叫停或改任务
- 计划创建本身必须很短：目标、轨道、成员、DAG、验收命令；不在主对话里替成员干活
- 主对话不得修改成员正在改的文件；冲突时排队
- 跨项目派发不建队承载（见「派发」）：主线直接 `awf-dispatch`（默认异步，需要结果时显式 `--wait`），不在团队里设 dispatcher 成员层；只有豁免场景才直接在主线处理

## 7. 发起口令

```text
用 AgentTeams 按 docs/team-flow.md 执行：<一句话目标>
```

队长据此贴 3 行计划摘要（轨道 + 成员 + DAG + 质量合同）并自动建队（`approval=automatic`，用户已授权）；建队后仍可立即叫停或改任务。

## 8. 附录：计划模板（复制后改）

```text
目标：<一句话交付物>
轨道：B/dev
成员：implementer（实现）、reviewer（独立复核）

t1 实现：kind=implementation
  inScope: <文件/目录>
  verify: <必须实际执行的命令>
  acceptance: <可判定的结果>

t2 复核：kind=review，deps=t1，reviewedTaskId=t1
  要求：独立重跑 verify；输出 verdict + findings

队长：建队前登记 <type>-xxx；收尾归档 → check → status → commit
```

# 满池治理：归档台账 / --new 上限 / 并发互斥 / --cleanup

关联任务：DEV-214（2026-11-07）。

## 背景

每项目 [awf] 会话上限 3 个（DEV-134/DEV-210 定），DEV-212 满 3 全忙→监听等待。
满池监听等待逻辑暴露四个缺陷：归档会话仍占池；--new 静默绕过上限；并发新建竞态；
没有清理手段把超限空闲会话归档掉。

## 决策与修法

1. **本地归档台账** `dispatch/archived-sessions.json`（派发方 cwd，.gitignore 已忽略 dispatch/）：
   记录 `{sessionId, project, title, archivedAt}`；`select_reuse_session` / `project_awf_pool`
   （统计/监听池）统一排除台账 id；`--forget-archived` 删除文件重置。读损坏/缺失保守返回空集。
2. **--new 上限校验**：池 ≥3 且**全忙**才拦（`over_limit_guard`）；需 `--allow-over-3` 显式确认，
   确认后 session_note 写入派发日志留痕（`- 会话提示：超上限新建（--allow-over-3 确认）`）。
   「池满但有空闲」不拦——--new 隔离/调试语义仍成立，且与需求措辞「池≥3 且全忙」一致。
3. **并发新建互斥**：`dispatch/.lock-<project>` 文件锁（fcntl.flock，非 Unix 退化空操作）。
   **锁只包「重读 + 决策 + 创建」快路径**，拿到锁后 `api.sessions()` 重读池再决策
   （decide_new_session）：有可复用候选（并发方刚建）→ 改复用；忙碌候选 → 锁外等空闲。
   排队等待（最长 180s）绝不在锁内做，否则阻塞同项目其它派发。
4. **--cleanup**：按项目聚合 [awf] 会话，保留最近更新 3 个（含运行中），其余**空闲**者为候选、
   运行中跳过；`--apply` 经 `workspace/archiveSession` 归档并写台账；默认 dry-run 与 --prune 同风格。
   RPC 端点名按任务规格 `workspace/archiveSession`（request.sessionId），不支持时逐会话报错退出 2。

## 踩坑（复用）

- **Python docstring 里混用 `.format()` 与字面 `{...}` 会 KeyError**：返回结构描述里的花括号
  必须写成 `{{}}` 转义（collect_cleanup_candidates / collect 系列都中过）。
- macOS `tempfile.TemporaryDirectory()` 返回 `/var/...` 而 `os.getcwd()` 返回 `/private/var/...`
  （/var 是符号链接）：断言 cwd 相对路径时用 `Path.cwd()` 派生，别用 tmp 原串直接拼。
- `--new` 走 `dest="reuse" store_false`，运行时别再用独立的 `args.new`；互斥/校验一律看 `args.reuse`。
- 测试桩 FakeApi 不继承 DshApi：锁内重读用 `isinstance(api, DshApi)` 门控，桩类直接复用预检快照，
  保持「--new 不碰 session/list」的既有测试语义（NoListApi calls==0）。
